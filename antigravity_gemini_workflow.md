# Выполнение задачи в Antigravity + Gemini

**Продуктовый срез: 08.09.2026, официальная документация Antigravity 2.0; установленный интерфейс может отличаться.** Контракт, границы и verification сохраняются при смене версии или модели. Настройка Qwen Project Brain — [onboarding](ai_onboarding.md); получение задания — [playbook](prompting_playbook.md).

## 1. Подготовьте рабочую копию

Для заданий расписания следуйте [Git contribution workflow §1–3](git_contribution_workflow.md): свой fork (`origin`), основной repository (`upstream`), свежий `main`, отдельная feature-ветка. Если clone ещё нет, сначала получите локальную копию **своего** fork; инструкции запуска находятся в README приложения. Репозиторий подготовки содержит Markdown, приложения для запуска в нём нет.

Первый clone: на GitHub откройте учебный repository → создайте свой **Fork** → в своём fork скопируйте HTTPS URL из **Code**. В терминале выполните `git clone URL_ВАШЕГО_FORK`, затем перейдите в созданную папку командой `cd utm-curs-i-orar-2027`. Обозначение URL замените скопированным адресом. Дальше добавьте `upstream` и подготовьте новую ветку по ссылке выше.

Перед первым запуском прочитайте README приложения и требования runtime. В [проверенном учебном срезе](https://github.com/barbalatv/utm-curs-i-orar-2027/tree/6e5bc45f478272e80153fa112132051e885ccaea) CI использует Node.js 22: зависимости устанавливаются через `npm ci`, локальный запуск — `npm run dev`. Следуйте README по локальному окружению; содержимое секретов в чат не передавайте. В другой версии команды сначала перепроверяются.

В терминале внутри рабочей папки выполните:

~~~bash
git rev-parse --show-toplevel
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short
~~~

Первая команда показывает папку repository, следующие — remotes, ветку, полный SHA и локальные изменения. Запишите starting/base SHA до работы. Пустой вывод `status --short` означает отсутствие перечисленных Git изменений, а не успешные тесты. Если в URL remote случайно записан токен, не пересылайте его модели.

Если есть чужая или прежняя незавершённая работа, не поручайте агенту её стирать. Сохраните и разберите состояние по существующему Git workflow; при расхождении истории не делайте автоматический reset/force-push. Git history нужен для понятных checkpoints и handoff; искусственно «украшать» его не требуется ([operating decisions §11](operating_decisions.md)).

## 2. Откройте repository в Antigravity

На 08.09 инструкция для Antigravity 2.0: при необходимости установить приложение с официального сайта; в левой панели значок папки с «+» → **New Project → Add Folder → Create**. Добавьте локальный clone приложения. Новый разговор предлагает **Local Mode** (работа в открытой папке) или **New Worktree Mode** (другое рабочее дерево Git). [Getting Started](https://antigravity.google/docs/getting-started/).

Для первого упражнения достаточно Local Mode в уже подготовленной feature-ветке. Для независимо работающего Builder используйте отдельный worktree по командному процессу; проверьте фактические папку, branch и base **после** его создания. Настройка Project не гарантирует, что автоматически выбрана нужная база. [Antigravity Projects](https://antigravity.google/docs/projects/).

Worktree отделяет файлы, но не БД, порты или секреты. Их разведение и владение schema/lockfile уже описаны в [AI workflow §4](ai_workflow.md). Второго Builder в ту же изменяемую папку новичку добавлять незачем.

В селекторе модели под полем ввода выберите **Gemini 3.8 Flash**, если она доступна. Официальная таблица на 08.09 перечисляет её в Antigravity на всех указанных планах; индивидуальные квоты различаются. Большие лимиты команды — наша исходная доступность, а не обещание безлимита для всех. Не переносите квоту Antigravity на Gemini API работающего продукта. [Models](https://antigravity.google/docs/models), [Plans](https://antigravity.google/docs/plans).

### Режим и права — разные настройки

**Planning Mode** предполагает исследование и план; **Fast Mode** — прямое выполнение локальной задачи. Для средней/рискованной работы полезно прочитать Plan перед реализацией. В **Artifact Review Policy** есть `Request Review` и `Always Proceed`; первый позволяет проверить предложенные изменения до продолжения. Это рекомендация для знакомства с инструментом, не обязательная пауза на каждый шаг. [Artifact Review](https://antigravity.google/docs/artifact-review/).

Запуск команд регулируется отдельно: **Terminal Command Auto Execution** содержит `Request Review`, `Proceed in Sandbox`, `Always Proceed`. Начните с понятных вам прав; просмотр плана не является разрешением любой команды. Прочитайте запрос перед подтверждением, особенно если он меняет зависимости, удаляет файлы или публикует результат. Доступ за пределы Project и доступность sandbox зависят от настроек и ОС; не обещайте на Windows механизм, описанный для Linux/macOS. [Agent Settings](https://antigravity.google/docs/agent-settings).

### Постоянные правила — необязательное удобство

На 08.09 Rules открываются через **Customizations → Rules**; есть Global и Workspace rules. Документация указывает `~/.gemini/GEMINI.md` и `.agents/rules`, с поддержкой прежнего `.agent/rules`. Для первого прохода достаточно самодостаточного prompt. Не создавайте второй набор командных policies; если сохраняете правило, пусть оно кратко направляет к документам и контракту. [Rules](https://antigravity.google/docs/rules-workflows/).

## 3. Передайте контракт и дайте выполнить задачу

В новый разговор внутри нужного Antigravity Project вставьте готовый контракт от Project Brain (по умолчанию Qwen). Добавьте разрешённый sample и локальный diff, если они входят в задачу. Фраза «смотри мой Qwen Project» не передаёт контекст Gemini. Исполнитель может самостоятельно исследовать любой относящийся к делу код; контракт ограничивает запись и authority.

Агент должен сначала проверить repository и состояние, прочитать относящиеся к делу инструкции и файлы, затем выполнить задачу в write scope. Если фактический SHA не соответствует контракту, обновите контракт по новому Recon. Если изменился только человек-владелец, перенесите ответственность в handoff; переписывать постановку с нуля не нужно.

Следите за изменениями, которые влияют на смысл: совпадает ли план с acceptance, не попали ли в diff parser/config/зависимости, не потерян ли negative case. **Локальная ошибка запуска не расширяет scope.** Агент может диагностировать причину и вернуть blocker; менять общий конфиг ради снятия ошибки без расширения контракта нельзя.

Работа с Gemini 3.8 Flash не требует особого синтаксиса. Практический выигрыш даёт ограниченная задача с измеримым окончанием. Если агент повторяет один и тот же неудачный fix, верните его к входу, фактическому выводу и гипотезе; при необходимости остановите Builder и выполните read-only Recon. Большой ответ не повод запускать ещё несколько исполнителей.

При исчерпанной квоте сохраните состояние по WIP-блоку [agent_task](templates/agent_task.md). Передача резервной модели содержит тот же контракт, текущий HEAD, локальный diff, реальные проверки и следующий шаг. Квоты измеряются на drills, а выбор инструментария подчиняется существующей заморозке 18 сентября ([preparation](preparation.md)).

## 4. Проверьте результат в repository

В Antigravity 2.0 **VCS panel** доступна из боковой панели: можно смотреть изменения рабочей копии и branch diff. Отчёт или Walkthrough полезен как указатель, но проверять нужно файлы и фактическое поведение. [Feature overview](https://antigravity.google/docs/features).

В терминале просмотрите изменения относительно зафиксированной базы. В командах ниже `BASE_SHA` заменяется полным SHA из контракта; это обозначение, не готовое имя Git ref:

~~~bash
git rev-parse HEAD
git status --short
git diff --stat BASE_SHA
git diff BASE_SHA
git ls-files --others --exclude-standard
git diff --check BASE_SHA
~~~

`git diff BASE_SHA` показывает tracked-изменения от базы, включая локальные. **Новые untracked-файлы в этот diff не входят:** прочитайте каждый файл из последней команды отдельно. `git diff --check BASE_SHA` ловит часть проблем пробелов и маркеров, но не проверяет поведение программы. Для опубликованных commits полный PR diff и история проверяются командами из [Git workflow §6](git_contribution_workflow.md).

Запустите команды из контракта в **той папке/worktree**, где находится изменение. Сопоставьте каждое acceptance с evidence: тест логики, настоящий ответ API или ручная процедура с входом и наблюдением. Для UI нужен просмотр поведения, включая responsive при его изменении. Screenshot показывает состояние экрана; он не доказывает правильность ветки, расчёта или failure case.

Не угадывайте команды по стеку. В учебном приложении их ищут в `package.json` и CI; для другого repository они могут отличаться. Если тест не стартовал из-за окружения, это blocker проверки. Запишите ошибку и что осталось непроверенным; не называйте это ни PASS, ни доказанным дефектом feature.

## 5. Верните evidence в исходный Qwen step-chat

Единственный формат — раздел **«Формат результата»** в [templates/agent_task.md](templates/agent_task.md). Попросите Antigravity заполнить его и приложить материалы: фактические изменения/все файлы/причины, base/HEAD и `git status`, реально выполненные команды с фактическим выводом, diff/patch/changed blocks и новые файлы, непроверенное, dependencies/lockfile/config/schema/shared contracts («нет» тоже ответ), риски и следующий шаг интегратора.

Команды §4 дают tracked diff от base, включая уже сделанные checkpoints, staged и unstaged изменения. Untracked-файлы нужно приложить отдельно. Для небольшого изменения перенесите в чат относящиеся hunks с контекстом и фактический вывод проверок вместе с полным inventory/status; для рискованного — полный релевантный diff и evidence отказов. Выбирайте минимальный достаточный пакет, сохраняя полный человеческий Scope gate. Если в пакете оказались секреты/недопустимые данные, исключите их содержимое и явно обозначьте ограничение review, не скрывая сам факт изменения файла.

SHA одного HEAD недостаточно для незакоммиченной работы: зафиксируйте `HEAD + working diff` и новые файлы. Public GitHub показывает опубликованную baseline, но не локальную реализацию, status или незапушенные commits. Не нужно публиковать изменения только ради Qwen. Проверки должны описывать именно переданное состояние; после последующих правок повторите относящиеся проверки и обновите пакет. Отчёт/Walkthrough без diff и подтверждающих выводов не заменяет evidence.

1. Откройте **тот же Qwen chat**, где составляли контракт. Вставьте handoff и материалы либо приложите patch/файлы/выводы к сообщению. Это материалы конкретного шага; постоянные 5 Source slots расходовать на его debugging не требуется.
2. Используйте копируемый **advisory review** из [agent_task](templates/agent_task.md). Qwen сравнивает evidence с исходным objective, negative case, scope/запретами, acceptance и рисками; не выдаёт чтение лога за собственный запуск.
3. `FIX REQUIRED`: перенесите созданный Qwen targeted fix-up в текущую задачу Antigravity. Исправление сохраняет правильную часть и остаётся в исходном scope. После повторных проверок верните обновлённые материалы в исходный Qwen chat. Новый существенный шаг потребует нового чата, этот fix-up — нет.
4. `BLOCKED: MISSING EVIDENCE`: получите именно названный diff, вывод или воспроизведение; не запускайте произвольный redesign. `ACCEPTABLE`: существенного нарушения не найдено и evidence достаточно для следующей человеческой проверки; это не гарантия и не право модели разрешать commit.

## 6. Человеческая приёмка и Git

Человек отвечает на три вопроса: могу ли объяснить каждый изменённый файл; где доказательство positive и negative case; какой риск остался. Независимость Qwen от исполнителя полезна, но согласие моделей не является verification. Полный lifecycle и учебный fix-up — в [playbook §2–3](prompting_playbook.md).

Local commit/checkpoint не равен готовности ветки/PR. Review можно сделать по локальному diff до commit или по существующему checkpoint вместе со всем состоянием. Особенно полезен он перед заявлением готовности шага/ветки; нового обязательного разрешения модели на каждый commit нет. Далее действует [Git contribution workflow](git_contribution_workflow.md): human Scope/Behaviour/Ownership/Handoff, отдельно merge/integration и release по правам [Integrator / Technical Deputy](strategy.md). Accepted учебный PR не обязательно merge в продукт. После интеграции проверяется сквозной сценарий на объединённой версии.

Если Qwen недоступен или переключение неоправданно, [Antigravity-only fallback](ai_onboarding.md) сохраняет работу: intent → Antigravity recon/planning → human review постановки → execution → human evidence review. Контракт и handoff те же; независимого Project Brain в этом режиме нет.

Первый завершённый проход должен оставить объяснимый scope, состояние, positive/negative evidence, review recommendation, непроверенное и понятный человеку handoff. Командные workstreams и evaluation — следующий уровень в [ai_workflow](ai_workflow.md).
