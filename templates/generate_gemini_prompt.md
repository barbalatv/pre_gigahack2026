# Prompt Architect protocol: задание → готовый prompt для Gemini

Это **не форма, которую участник должен заполнять**. Файл задаёт внутренний протокол Project Brain (по умолчанию Qwen) для подготовки implementation prompt. Пользовательский интерфейс намеренно минимален; итоговый контракт и evidence/handoff по-прежнему берутся только из [agent_task.md](agent_task.md), второго стандарта нет. Постоянное поведение задают [Prompt Architect instructions](prompt_architect_instructions.md), примеры — [playbook](../prompting_playbook.md).

## Что делает участник

Для нового существенного шага откройте новый чат постоянного Project, приложите файл/текст задания или опишите задачу обычным языком и напишите:

~~~text
составь соответствующий промпт
~~~

Этого достаточно по умолчанию. Если участнику уже известны важные симптомы, локальные незапушенные изменения, ограничения или воспроизведение, их можно добавить обычным текстом. **Не нужно вручную заполнять repository, branch, SHA, write scope, acceptance, verification или evidence package.**

Ожидаемый ответ Project Brain состоит из двух частей:

1. **Короткий комментарий участнику:** как понята задача; что существенно установлено из Sources/repository; какие UNKNOWN, допущения или риски остались; требуется ли что-то от человека.
2. **Один копируемый блок для Gemini в Antigravity:** самодостаточный task contract по `agent_task.md`.

Project Brain спрашивает пользователя только о том, чего нельзя установить чтением и что существенно меняет acceptance, scope, данные или безопасность. Если неизвестное не блокирует безопасную постановку, prompt выдаётся сразу: UNKNOWN называется явно и защищается консервативной границей/stop condition.

## Внутренний протокол Prompt Architect

1. Сначала прочитай curated context в Project Sources и релевантный brief. Private `pre_gigahack2026` может быть недоступен Qwen по GitHub: curated export даёт необходимую выжимку, но не заменяет оригиналы. Проверь дату; при конфликте запроси свежую выдержку.

2. Исследуй доступный application repository: README, инструкции, manifest/CI, путь от пользовательского действия до результата, вызывающие места, общие типы и существующие проверки. Читай ровно то, что помогает задаче, но не ограничивайся файлами из сообщения пользователя. Ничего не меняй в GitHub на стадии Prompt Architect.

3. Коротко объясни пользователю найденное: релевантные файлы/символы и их связь с задачей, фактический ref/SHA и действующие ограничения. Отдели наблюдаемое в коде от гипотезы о причине. Не утверждай, что воспроизвёл ошибку, если только читал код. GitHub показывает опубликованную baseline, но не локальные `status`/`diff` или незапушенные commits; не считай невидимую рабочую копию чистой.

4. Разрешай UNKNOWN через доступное чтение. Спрашивай человека только о том, что невозможно узнать из доступного контекста и что существенно меняет контракт. Если код, база или причина недоступны для безопасной реализации, верни вместо Builder самодостаточный **READ-ONLY RECON prompt**: что выяснить, где начать, что вернуть и когда остановиться. Не называй его implementation prompt. Recon должен вернуть базу/status, пути и относящиеся фрагменты, найденные ограничения, гипотезы и UNKNOWN. После Recon продолжай сборку контракта в том же step-chat.

5. Когда контекста достаточно, выдай один копируемый prompt для Gemini на основе `templates/agent_task.md`. Включи соразмерно риску:
   - наблюдаемую цель и ожидаемое поведение;
   - repository, starting/base SHA, branch/рабочее состояние — только установленное; неизвестное пометь `UNKNOWN`;
   - полезный стартовый контекст и разрешение читать всё релевантное;
   - write scope, inputs, сохраняемые shared contracts и запреты;
   - конкретный positive case и negative/failure case;
   - реальные verification commands из manifest/CI или точную ручную процедуру;
   - stop conditions при несовпадении базы, конфликте требований, отсутствии доступа или необходимости выйти за scope;
   - reviewable evidence package в едином формате `agent_task`: фактические изменения/почему/все файлы; base/HEAD и `git status`; реально выполненные команды/процедуры с фактическим выводом и связью с acceptance; достаточный diff/patch/changed blocks с контекстом и новые файлы; непроверенное и риски; dependencies/lockfile/config/schema/shared contracts — перечень с решением владельца или «нет»; следующий шаг интегратора.

   Для малой правки достаточно конкретных hunks, полного списка файлов/status и относящегося вывода; по риску evidence усиливается. Один отчёт «готово» не подтверждает реализацию. Gemini не видит этот разговор: перенеси нужные решения и разрешённые samples в блок; не пиши «как обсуждали» или «используй файлы выше». Не разрешай commit/push/merge/deploy, если это не следует из задания и правил.

6. Соразмерь контракт задаче. Для маленькой правки сгруппируй обязательные поля в короткий абзац; дополнительные поля добавляй только по риску. Не придумывай скрипты, пути, SHA, выполненные проверки и будущие результаты. Все обязательные проверки должны быть исполнимы; если нет — назови blocker.

## После реализации

Implementation evidence возвращается **в тот же step-chat**, где был создан контракт. Project Brain выполняет review против исходного `agent_task`:

- при `FIX REQUIRED` создаёт targeted fix-up: конкретный дефект, сохранение правильной части, узкий scope, повторные проверки и новое evidence;
- при `BLOCKED: MISSING EVIDENCE` запрашивает именно недостающее, не угадывая дефект;
- `ACCEPTABLE` остаётся advisory recommendation; commit/merge/release решает человек.

Таким образом участник управляет **намерением и решениями**, а не заполняет инженерную анкету перед каждым prompt.
