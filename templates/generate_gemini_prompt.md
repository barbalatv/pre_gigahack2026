# Generate an implementation prompt for Gemini

Вставьте блок в **новый чат для существенного шага** в Project Brain (по умолчанию Qwen) и допишите намерение. Repository приложения и его локальное состояние нужны, если они ещё не известны из текущей задачи. Это запрос к **Prompt Architect**; итоговый контракт и evidence/handoff берутся из [agent_task.md](agent_task.md), второго стандарта нет. Инструкции — [универсальное ядро](prompt_architect_instructions.md), примеры — [playbook](../prompting_playbook.md).

~~~text
Подготовь готовое задание для Gemini в Antigravity. Пока не реализуй его.
Моё намерение: [например: нужно исправить обновление списка после сохранения].
Repository приложения: [URL, если ещё не указан].
Рабочая branch / starting SHA / локальные изменения: [известное или UNKNOWN].
Особые ограничения / воспроизведение: [если есть; иначе найди в контексте].

1. Сначала прочитай curated context в Project Sources и релевантный brief.
Private pre_gigahack2026 недоступен Qwen по GitHub: экспорт даёт выжимку
operating_decisions.md, ai_workflow.md и templates/agent_task.md, но не
заменяет оригиналы. Проверь дату; при конфликте запроси свежую выдержку.
Затем исследуй доступный public repository приложения: README, инструкции, manifest/CI,
путь от пользовательского действия до результата, вызывающие места,
общие типы и существующие проверки. Читай ровно то, что помогает задаче,
но не ограничивайся файлами из моего сообщения. Ничего не меняй в GitHub.

2. Коротко покажи найденное: файлы/символы, их связь с задачей, фактический
ref/SHA, действующие ограничения. Отдели наблюдаемое в коде от гипотезы
о причине. Не утверждай, что воспроизвёл ошибку, если только читал код.
GitHub показывает опубликованную baseline, не локальные status/diff или
незапушенные commits. Не считай невидимую рабочую копию чистой.

3. Разреши неизвестные через доступное чтение. Спроси только то, что нельзя
узнать из repository и что меняет acceptance или границы. Если код,
база или причина недоступны для безопасной реализации, верни вместо Builder
самодостаточный READ-ONLY RECON prompt: что выяснить, где начать, что вернуть,
когда остановиться. Не называй его готовым implementation prompt.
Recon должен вернуть базу/status, пути и относящиеся фрагменты, найденные
ограничения, гипотезы и UNKNOWN. Это рабочий путь и для private приложения.
После Recon используй эти материалы для продолжения с пункта 4 в том же чате.

4. Когда контекста достаточно, выдай один копируемый блок для Gemini
на основе templates/agent_task.md. Включи:
- наблюдаемую цель и ожидаемое поведение;
- repository, starting/base SHA, branch/рабочее состояние;
- полезный стартовый контекст и разрешение читать всё релевантное;
- write scope, inputs, сохраняемые shared contracts, запреты;
- конкретный positive case и negative/failure case;
- реальные verification commands из manifest/CI или точную ручную процедуру;
- stop conditions при несовпадении базы, конфликте требований, отсутствии
  доступа или необходимости выйти за scope;
- reviewable evidence package в едином формате результата agent_task:
  фактические изменения/почему/все файлы; base/HEAD и git status; реально
  выполненные команды/процедуры с фактическим выводом и связью с acceptance;
  достаточный diff/patch/changed blocks с контекстом и новые файлы;
  непроверенное и риски; dependencies/lockfile/config/schema/shared contracts
  — перечень с решением владельца или «нет»; следующий шаг интегратора.
  Для малой правки достаточно конкретных hunks, полного списка файлов/status
  и относящегося вывода; по риску evidence усиливается. Один отчёт «готово»
  не подтверждает реализацию. GitHub baseline не содержит локальный diff.
Gemini не видит этот разговор: перенеси нужные решения и разрешённые samples
в блок; не пиши «как обсуждали» или «используй файлы выше».
Не разрешай commit/push/merge/deploy, если это не следует из задания и правил.

5. Соразмерь контракт задаче. Для маленькой правки сгруппируй обязательные
поля в короткий абзац; дополнительные поля только по риску. Не придумывай
скрипты, пути, SHA, выполненные проверки и будущие результаты. Все обязательные
проверки должны быть исполнимы; если не исполнимы, назови blocker.

После блока укажи оставшиеся риски/вопросы приёмки и напомни вернуть
implementation evidence в этот же чат для review против исходного контракта.
При FIX REQUIRED создай targeted fix-up по тому же agent_task: конкретный
дефект, сохранение правильной части, узкий scope, повторные проверки и новое
evidence. При MISSING EVIDENCE запроси недостающее; не угадывай дефект.
ACCEPTABLE — advisory recommendation; commit/merge/release решает человек.
~~~
