# Практические задания команды и lessons learned

**Срез: 8 сентября 2026.** Этот документ фиксирует **OBSERVED PRACTICE** из первых командных упражнений и **RECOMMENDATION** на следующие. Это не правила GigaHack и не замена шести drills из [preparation.md](preparation.md).

Учебный репозиторий: [barbalatv/utm-curs-i-orar-2027](https://github.com/barbalatv/utm-curs-i-orar-2027).

## 0. Зачем мы вообще даём маленькие задания

Цель упражнений — не проверить, кто быстрее пишет React-код. Мы тренируем полный путь, который понадобится на хакатоне:

> **TASK CONTRACT → AI AGENT → INSPECT DIFF → VERIFY → PR → REVIEW**

Полезный результат — не «код появился», а **человек сумел получить узкое изменение, понять его, проверить и передать на приёмку без мусора вокруг**.

Поэтому маленькое техническое изменение может быть хорошим упражнением даже тогда, когда сама функция тривиальна. Оно вскрывает проблемы с Git, контекстом для AI, scope control, проверкой responsive UI и способностью читать собственный diff.

## 1. Задание №1 — contribution path

**Назначение:** пройти весь путь от форка до PR на максимально простой функции, чтобы Git и запуск не смешивались со сложностью логики.

Рабочая постановка:

1. Синхронизировать форк с актуальным `main` исходного репозитория.
2. С чистого состояния локально запустить проект.
3. Создать **отдельную feature-ветку** от актуального `main`.
4. Сделать **одно небольшое видимое текстовое/UI-изменение**.
5. Не менять архитектуру, зависимости, конфигурацию, parser/domain logic и секреты ради этого задания.
6. Посмотреть итоговый diff целиком.
7. Сделать осмысленный commit, push ветки и PR в основной репозиторий.
8. Приложить скриншот результата и кратко написать: что изменено, что проверено, где помогал AI и была ли проблема.

**Критерий приёмки:** приложение запускается; нужное изменение видно; PR содержит только относящиеся к задаче изменения; участник может объяснить каждый затронутый файл.

### Что это упражнение неожиданно хорошо проверило

- умеет ли человек отличать свой форк от upstream-репозитория;
- создаёт ли новую ветку или продолжает старую;
- замечает ли generated/случайные изменения;
- пытается ли «лечить» локальную ошибку изменением конфигурации проекта;
- смотрит ли на diff до PR;
- понимает ли, что работающий локально код ещё не означает хороший PR.

## 2. Задание №2 — счётчики занятий на кнопках дней недели

**Назначение:** усложнить не Git, а именно контракт функции и работу с AI внутри существующего кода.

### Требуемое поведение

В режиме **`Azi`** на кнопках дней недели нужно показывать количество занятий **выбранной группы на текущей учебной неделе**.

Требования:

- считать только занятия выбранной группы;
- учитывать текущую чётность недели через существующую логику проекта;
- занятия другой чётности не считать;
- если занятий нет — показывать `0`;
- переключение между днями должно продолжать работать;
- desktop и mobile UI не должны ломаться или переполняться;
- мобильный вид можно и нужно проверять через responsive mode браузера, отдельный телефон не обязателен;
- не добавлять новые библиотеки ради этой функции;
- не менять parser, общую модель данных, конфигурацию и соседние функции без необходимости, вытекающей из задания.

AI-ассистент здесь является частью упражнения: проверяется не способность написать всё вручную, а умение дать агенту контракт, позволить ему осмотреть релевантный код, затем **самостоятельно проверить его результат**.

### Что сдавать

- отдельную ветку от актуального upstream `main`;
- PR с понятным названием;
- screenshot desktop или mobile состояния, где счётчики видны;
- короткое описание проверки: выбранная группа, текущая чётность, день с `0`, переключение дня, responsive;
- одна-две строки о том, что предложил AI и что участник проверил/исправил после него.

## 3. Что обнаружилось на реальных PR

Ниже не рейтинг участников, а список отказов процесса, которые уже случились и потому должны стать частью подготовки.

### 3.1 Правильная функция поверх устаревшей базы всё равно даёт плохой результат

В нескольких PR feature-логика выглядела разумно, но форк был создан до крупных изменений upstream. В результате PR вместе с новой функцией пытался откатить или заменить уже существующие изменения приложения.

Пример: [PR #9](https://github.com/barbalatv/utm-curs-i-orar-2027/pull/9) содержал нужную идею со счётчиками, но diff одновременно затрагивал большой объём уже изменившегося приложения.

**Вывод:** stale fork — не косметическая проблема Git. Это источник функциональной регрессии. Актуальность base commit входит в критерий корректности задачи.

### 3.2 Нельзя продолжать второе задание в ветке первого

В [PR #10](https://github.com/barbalatv/utm-curs-i-orar-2027/pull/10) сама реализация счётчиков была в целом пригодной, но ветка продолжала предыдущую работу и несла старые изменения вместе с новой задачей.

**Вывод:** **одна задача = одна новая ветка от актуального upstream `main`**. Новая задача не начинается командой `git switch old-feature`.

### 3.3 Dirty diff может содержать реальный дефект, а не просто шум

В [PR #14](https://github.com/barbalatv/utm-curs-i-orar-2027/pull/14) вместе с UI-изменением в diff попали посторонние изменения; среди них была правка parser/domain logic, не относящаяся к задаче и способная сломать распознавание дней расписания.

**Вывод:** «лишние два файла» нельзя автоматически считать безобидными. Если файл не нужен задаче, участник должен понять, **почему он изменился**, и убрать изменение либо доказать необходимость.

### 3.4 Ошибка локального запуска не расширяет scope задания

На одном из выполнений участник удалил конфигурационный параметр, потому что локально возникла ошибка, и одновременно внёс несвязанное текстовое изменение.

**Правило:** если для решения UI-задачи внезапно требуется менять `baseUrl`, parser, lockfile или другую инфраструктуру — это **STOP-сигнал**, а не разрешение расширить задачу. Сначала диагностируется окружение или поднимается вопрос владельцу задачи.

### 3.5 AI хорошо пишет код и так же хорошо производит убедительный лишний код

Типовые ошибки из проверок:

- посчитать все занятия, забыв про чётность;
- поменять соседний UI ради удобства реализации;
- добавить лишний `useEffect`, хотя результат можно вычислить из уже имеющегося состояния;
- перепутать семантику существующего helper (`isOtherWeek` и похожие случаи);
- затронуть generated-файл или parser, потому что агент решил «почистить заодно»;
- решить локальную проблему конфигурацией репозитория вместо выполнения контракта.

**Вывод:** участник отвечает не за prompt, а за **принятый diff**. Фраза «это сделал AI» не объясняет ни одного изменения.

## 4. Новые критерии приёмки для учебных задач

Начиная со следующего упражнения задача считается выполненной только если проходят пять ворот.

### Gate A — Fresh base

Feature-ветка создана от актуального upstream `main`. Участник может назвать base commit или показать, что перед созданием ветки выполнил sync.

### Gate B — Scope

`git diff upstream/main...HEAD` содержит только изменения, нужные задаче. Нет старого задания, generated-мусора, форматирования всего файла и случайных правок конфигурации.

### Gate C — Behaviour

Проверен положительный сценарий и минимум один отрицательный/граничный сценарий из контракта.

### Gate D — Ownership

Участник может одним предложением объяснить каждый изменённый файл и ответить, почему изменение находится именно там.

### Gate E — Handoff

Ветка, commit и PR имеют понятные имена; PR содержит что изменено, что запускалось и screenshot/доказательство там, где оно применимо.

Если Gate A или B не проходят, сначала чинится история/ветка. Review бизнес-логики поверх заведомо грязного diff почти всегда тратит время впустую.

## 5. Когда проще выбросить ветку, чем «чистить» её

Да — часто **правильнее удалить загрязнённую feature-ветку и начать от свежего `main`**, чем пытаться лечить историю merge'ами.

Правило:

- если в старой ветке **нет полезной уникальной работы** — удалить её и создать новую;
- если есть один-два правильных commit — создать чистую ветку от `upstream/main` и `cherry-pick` только нужные commit;
- если изменение ещё не оформлено в commit — перенести только нужный diff вручную или через patch;
- не «синхронизировать» грязную ветку merge'ом с `main`, если это лишь делает историю сложнее.

Цель — не сохранить ветку. Цель — получить **маленький объяснимый PR**.

Подробные команды — в [git_contribution_workflow.md](git_contribution_workflow.md).

## 6. Практика AI, которую стоит переносить на хакатон

Из работы над расписанием отдельно подтвердился полезный паттерн для рискованных изменений:

~~~text
READ-ONLY RECON
      ↓
человек подтверждает факты и scope
      ↓
NARROW FIX / BUILDER
      ↓
исполняемая проверка
      ↓
INDEPENDENT PRE-COMMIT REVIEW
      ↓
commit / merge / deploy
~~~

Это не обязательная тройка моделей на каждую мелочь. Принцип **risk-triggered**:

- RECON не должен менять код, если сначала нужно понять причину;
- fix-agent получает только подтверждённые проблемы и границы изменения;
- независимый reviewer пытается опровергнуть diff до публикации для изменений с высокой ценой ошибки;
- согласие моделей не является доказательством — тест, diff, реальный ответ API и поведение приложения являются.

В одном из рабочих циклов роли были разведены как **Antigravity → RECON, Codex → narrow fix, Claude Code → независимый pre-commit review**. Ценность здесь не в названиях моделей, а в разделении полномочий: исследователь не чинит, implementer не сам себя утверждает, reviewer получает готовый diff.

Это конкретизация общего процесса из [ai_workflow.md](ai_workflow.md), а не новая архитектура агентов.

## 7. Как эти упражнения связаны с GigaHack

Задание №1 проверяет минимальный contribution path. Задание №2 уже моделирует реальный AI-assisted workstream: существующий код, ограниченный контракт, бизнес-правило, responsive UI, reuse существующих helpers и необходимость отбросить лишний output агента.

Их результаты полезны для распределения ролей:

- **Integrator / Deputy:** чистота diff, диагностика загрязнённой ветки, способность принять чужой PR;
- **Builder / Surge:** реализация по контракту без scope creep;
- **Data/Evaluation:** умение проверить условие чётности и контрпример, а не только happy path;
- **UX/Demo:** проверка mobile и видимого результата;
- **Product/Domain:** способность заметить, когда технический fix перестал соответствовать заданию.

Эти упражнения **не добавляют Drill G**. Они являются дешёвой подготовкой к drills B (AI implementation), C (integration) и E (Deputy), чтобы сами drills тратили время на узкие места команды, а не на объяснение Git с нуля.

## 8. Короткая формула для следующих заданий

Каждое следующее упражнение должно становиться сложнее только по **одной оси**:

1. сначала contribution workflow;
2. затем ограниченная функциональная логика;
3. затем два параллельных изменения и интеграция;
4. затем отказ/регрессия;
5. затем передача чужого кода Deputy.

Если одновременно дать новый Git-процесс, новый стек, сложный domain и новый AI-инструмент, мы измерим только способность пережить хаос.
