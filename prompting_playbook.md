# Как провести AI-задачу от намерения до принятого результата

**Ревизия 9 сентября 2026.** Рабочий цикл принят в [operating decisions §7](operating_decisions.md); примеры и приёмы ниже — RECOMMENDATION. Настройка контекста — [onboarding](ai_onboarding.md); выполнение — [Antigravity](antigravity_gemini_workflow.md); командная оркестрация — [AI workflow](ai_workflow.md). Здесь учимся управлять одной задачей: хороший prompt — только часть цикла.

## 1. Хороший prompt — компактный инженерный контракт

Natural language — нормальный интерфейс. Фраза «после сохранения покажи обновлённый список, сохрани фильтр; при ошибке оставь введённое и покажи сообщение» уже точнее, чем длинная просьба «действуй как senior». Проблема обычного чата — отсутствие контекста, цели, границ, состояния repository и проверки. Markdown помогает прочитать контракт; XML, JSON и специальные слова сами по себе не улучшают результат.

**Minimal context, unrestricted relevant inspection.** Дайте агенту короткую постановку, исходное состояние, вход и ключевые ограничения. Разрешите читать связанные вызовы, типы, тесты и документацию, даже вне области записи. Не отправляйте весь repository одним сообщением и не запрещайте смотреть дальше одного файла. Это правило из [AI workflow §4](ai_workflow.md).

| Почти всегда, для работы в repository | Добавлять, когда нужно |
|---|---|
| Наблюдаемая цель: что увидит пользователь | До/после, пример входа/выхода, если поведение неоднозначно |
| Repository, исходный SHA и рабочее состояние | Версия sample, PR/base сравнения, dirty diff, окружение |
| Область записи и то, что нужно сохранить | Общая схема/API, владелец миграций, порт и fixture для worktree |
| Положительный и отрицательный/граничный критерий | Несколько edge cases, latency, восстановление, повторный вызов |
| Проверка: точные команды или ручная процедура | Baseline/holdout/eval для измеримого AI-результата |
| Stop conditions и краткий handoff с риском | WIP-записка, передача интегратору, смена модели или владельца |

Для coding-задачи эти требования можно объединить в пять предложений. Поля владельца, числа параллельных задач и ветки из [agent_task](templates/agent_task.md) заполняются при выдаче workstream; новичку не нужно выдумывать командную загрузку. Для вопроса без изменения repository Git-поля не нужны.

## 2. Полный lifecycle: context → contract → evidence → review

~~~text
INTENT → CONTEXT → RECON if needed → TASK CONTRACT → EXECUTION
→ EVIDENCE → REVIEW → FIX-UP / ACCEPT → HUMAN COMMIT / INTEGRATE
~~~

Это provider-neutral интерфейс. В основном маршруте Project Brain — Qwen, Executor — Gemini в Antigravity. Совместимые альтернативы и fallback описаны в [onboarding §4](ai_onboarding.md); задача, evidence и полномочия от имени модели не меняются.

1. **INTENT.** Новый существенный шаг — новый чат постоянного Project. Используйте [генератор задания](templates/generate_gemini_prompt.md), скажите намерение своими словами. Добавьте симптомы и локальное состояние, которых Project Brain не видит. Человеку не нужно самому заполнять двадцать полей.
2. **CONTEXT.** Project Brain читает curated Sources, их версии и доступный public application repository: дерево, связанные вызовы, типы и проверки. Отделяет requirement от гипотезы и UNKNOWN. Private preparation передаётся через экспорт; private application — через целевые материалы, не выдуманный доступ.
3. **RECON if needed.** Если кода/базы/причины недостаточно, сначала read-only запрос исполнителю: какие вопросы разрешить, где начать, какие пути, фрагменты и состояние вернуть. Результат идёт в этот же чат. Критичное UNKNOWN нельзя заполнить догадкой; после фактов человек фиксирует границы, Project Brain собирает контракт. Если задача уже решена в новом main, контракт меняется или шаг закрывается без diff.
4. **CONTRACT.** Один самодостаточный блок по [agent_task](templates/agent_task.md). Человек сверяет цель, write scope, сохраняемые контракты и positive/negative acceptance. Проверка должна существовать и опровергать критерий: «тесты должны пройти» недостаточно. Перенесите решения и разрешённые samples в блок; другая среда не видит память Project Brain.
5. **EXECUTION.** Исполнитель сверяет базу и локальное состояние, читает всё релевантное, реализует в write scope и запускает реальные проверки. Несоответствие базы, неясное требование и необходимость выйти за scope возвращаются владельцу; ошибка окружения не даёт права менять config.
6. **EVIDENCE.** По единому handoff из agent_task вернуть base/HEAD, полный список файлов и status, фактические изменения, достаточный diff/patch/блоки с контекстом, команды и фактический вывод, непроверенное, риски и dependencies/lockfile/config/schema/shared contracts («нет» тоже ответ). Public GitHub видит опубликованную baseline, но не эту незакоммиченную реализацию.
7. **REVIEW.** Вернуть материалы **в тот же step-chat**, где создан контракт. Project Brain сопоставляет их с первоначальным намерением, найденными ограничениями и acceptance. В [agent_task](templates/agent_task.md) уже есть копируемый review-запрос; отдельного стандарта не требуется.
8. **FIX-UP / ACCEPT.** При конкретном дефекте Project Brain сразу выдаёт узкий fix-up на основе исходного контракта. Исполнитель сохраняет правильную часть, исправляет дефект, повторяет относящиеся проверки и возвращает новое evidence в этот же чат. При нехватке evidence получают материалы, а не переписывают реализацию наугад.
9. **HUMAN COMMIT / INTEGRATE.** Человек оценивает рекомендацию и проходит действующие Git gates. После завершения сохраняет короткий итог шага; следующий существенный шаг начинается в новом чате с актуальной базой.

### Что считается независимым review

Project Brain независим **от исполнителя**; исходный контракт намеренно остаётся у reviewer. Это полезно для сверки намерения и реализации, но не исключает общей ошибки постановки. Дополнительный контрпример и человеческая проверка важнее согласия двух моделей.

Review проверяет девять вещей: objective; negative case; write scope; запреты; соответствует ли verification acceptance; подтверждены ли заявления evidence; что осталось непроверенным; возникли ли новые архитектурные обязательства; достаточно ли оснований для следующего человеческого gate.

| Recommendation | Что означает | Следующий шаг |
|---|---|---|
| **ACCEPTABLE** | Существенного нарушения не найдено; evidence достаточно в пределах явно проверенного | Человек оценивает риск и готовность к действующему gate; это не гарантия и не разрешение commit |
| **FIX REQUIRED** | Конкретный defect / scope violation / missing acceptance | Для каждого severity, evidence и ожидаемое исправление; сразу targeted fix-up |
| **BLOCKED: MISSING EVIDENCE** | Реализацию нельзя честно оценить по представленному | Назвать точные недостающие hunks, вывод или процедуру и получить их |

**Плохой переход:** Gemini пишет «Готово, 47 тестов проходят», человек спрашивает «Можно коммитить?», reviewer соглашается без diff и выводов. **Рабочий переход:** reviewer знает исходный контракт, видит изменения и относящиеся результаты, проверяет их и ограничивает вывод доступным evidence. Он не выдаёт чтение test output за собственный запуск тестов.

Пакет должен быть самым компактным, который позволяет проверить утверждение: для маленькой правки — конкретные hunks с контекстом, полный список файлов/status и реальные наблюдения; для существенных общих изменений — полный релевантный diff, вызывающие места и сильнее проверки отказов. Если размер пакета мешает review, делите его на понятные части, сохраняя общий inventory и базу. Сокращение пакета для AI не отменяет человеческий просмотр **полного diff от base**.

### Где review стоит относительно Git

Наиболее полезная точка — после реализации и проверок законченного шага, до заявления готовности ветки/PR. Можно передать локальный diff до commit; уже сделанный рабочий checkpoint тоже подходит, если указан весь фактический scope. `ACCEPTABLE` не является обязательным разрешением каждого local commit.

Local commit/checkpoint, branch completion/PR, merge/integration и release различаются. Порядок contribution и учебные gates — в [Git workflow](git_contribution_workflow.md) и [team rehearsal](team_rehearsal.md). По таблице решений [strategy §4](strategy.md): merge в main — Integrator или Technical Deputy; release/freeze — Integrator. Accepted учебный PR не обязан попасть в продукт. После интеграции проверяется объединённая версия, а не только успешная отдельная ветка.

### Маленькая: уточнить текст мобильной навигации

**Намерение человека:** «На мобильном экране надпись “Toate” слишком неясная; хочу “Grupe”.» Если вы знаете строку и можете проверить экран, вручную будет быстрее. AI можно дать только проверку связанных мест.

**Запрос Project Brain (по умолчанию Qwen):**

> Найди в учебном repository мобильную кнопку режима всех групп. Подготовь короткий prompt для Gemini: поменять только видимую подпись «Toate» на «Grupe». Сохрани desktop-подпись и выбор режима. Проверь, не используется ли текст как ключ. Не реализуй.

**Пример prompt для Gemini после чтения кода:**

~~~text
Repository: barbalatv/utm-curs-i-orar-2027.
Starting/base SHA: 6e5bc45f478272e80153fa112132051e885ccaea.
Работай в отдельной чистой feature-ветке от этой базы; при другом SHA
или неожиданном dirty state остановись и сообщи расхождение, без reset.
В src/components/ScheduleApp.tsx замени только мобильную видимую подпись
режима all с «Toate» на «Grupe». Desktop «Toate grupele», значение all,
обработчики и остальные подписи сохрани. Можно читать любой релевантный код;
писать только в этот файл. Конфиг, зависимости и форматирование не трогай.
Проверь в локальном приложении после npm run dev: при ширине 390 px видна
«Grupe», кнопка открывает все группы, затем «Azi» переключает обратно.
Граница: на 320 px навигация не переполняется; при 1280 px desktop-подпись прежняя.
Прочитай полный diff. Если это требует изменения layout или иных файлов,
сообщи причину и остановись до расширения scope. Верни файл/причину,
status/base/HEAD, hunk с контекстом и перечень файлов, фактические шаги
и наблюдения, непроверенное и риск; dependencies/lockfile/config/schema/
shared contracts — «нет» либо точный перечень. Не commit/push/deploy.
~~~

**Что ожидается от Gemini:** узкая правка и фактическая запись ручной проверки с размером viewport; при недоступном браузере — «UI не проверен» и процедура для человека. Новый тест, проверяющий лишь строковый литерал, здесь не нужен.

**Review:** человек смотрит, что diff не затронул верхнюю desktop-навигацию и значение `all`, затем нажимает кнопки. Полезный отдельный запрос AI: «Read-only: найди другие употребления этих подписей и риск изменения; не исправляй». Даже этот запрос избыточен, если связанные места уже очевидны.

**Намерение:** «Добавь количество пар рядом с каждым днём в “Azi”.» Фраза «Добавь счётчики» не задаёт группу, чётность, пустой день и семантику единицы счёта. Агент может посчитать все записи или использовать обратный смысл `isOtherWeek`.

**Запрос Project Brain (по умолчанию Qwen):**

> Используй разрешённую выдержку задания №2 из private team_rehearsal.md: счётчики дней в Azi для выбранной группы и текущей чётности, нулевой день и mobile. Если требование неясно, запроси точную выдержку. Найди в repository фильтрацию группы, дни и текущую чётность. Подготовь prompt Gemini с reuse существующей логики, проверкой нуля и mobile. Покажи, какие файлы подтверждают выбор scope.

**Пример prompt для Gemini:**

~~~text
Repository: barbalatv/utm-curs-i-orar-2027.
Starting/base SHA: 6e5bc45f478272e80153fa112132051e885ccaea.
Отдельная чистая feature-ветка; другой SHA/неожиданные локальные изменения —

Проверь 320/390/1280 px: числа видны, навигация не переполняется.

и новые файлы; UI-наблюдения; непроверенное; dependencies/lockfile/config/
~~~

**Ожидаемый результат Gemini:** объяснимый diff, тесты вычисления и запись проверки UI. Это форма ожидаемого результата, не утверждение «PASS».

**Review/verification:** handoff, diff и реальные выводы возвращаются в исходный Qwen step-chat. Reviewer проверяет знак фильтра, случай другой чётности, пустой день и UI evidence против контракта; недостаток материалов обозначает `BLOCKED: MISSING EVIDENCE`. Человек проверяет экран и весь diff: попутная правка parser/config не проходит Scope gate. Итог — по [agent_task](templates/agent_task.md).

### Сложная: видимый сбой обновления и ручной повтор

**Намерение:** «Расписание уже открыто, но при сбое обновления человек должен увидеть проблему и повторить загрузку, не потеряв свой выбор.»

Это **предлагаемое учебное изменение поведения** на реальном коде. Чтением установлено: `load` записывает `loadError`; UI-ветка ошибки обусловлена `!schedule`; периодическое клиентское обновление — раз в 10 минут. Отдельное серверное сообщение `staleNotice` основано на `status.source.last_result`. Эти два отказа нельзя путать. Браузерное воспроизведение в рамках написания документа не проводилось.

**Запрос Project Brain (по умолчанию Qwen):**

> Прочитай цепочку загрузки ScheduleApp → loadCourse и тесты. Подготовь сначала read-only Recon: выяснить поведение при уже показанных данных, при первой загрузке и при позднем ответе прежнего курса. После фактического отчёта собери ограниченный prompt Gemini на видимую ошибку и ручной повтор. Сохрани API и защиту 1 → 2 → 1; backend менять не нужно.

**Recon должен вернуть:** путь вызова с файлами; чем отличаются клиентский сбой и серверный stale status; как воспроизвести оба состояния; существующие тесты; разрешённый scope и неизвестное. Человек подтверждает, что нужен именно этот новый UX, затем выдаёт Builder contract.

**Пример prompt Gemini после такого решения:**

~~~text
Repository: barbalatv/utm-curs-i-orar-2027.
Starting/base SHA: 6e5bc45f478272e80153fa112132051e885ccaea.
Отдельная чистая feature-ветка. Перед записью проверь repository, HEAD, status.
При несовпадении с базой остановись для нового Recon; не возвращай историю назад.

Objective: при клиентском сбое обновления уже показанного расписания текущего
курса сохранить его на экране, явно сказать, что обновление не удалось,
и дать действие «Reîncearcă». Успешный повтор показывает согласованную новую
пару schedule/status и снимает сообщение. При первой неудачной загрузке,
когда данных ещё нет, показать понятную ошибку с тем же действием.

Контекст: ScheduleApp.load вызывает loadCourse; ошибка хранится в loadError.
~~~

**Независимое от исполнителя review в исходном Qwen step-chat:**

На названном base и полном релевантном diff попробуй опровергнуть acceptance: старый ответ курса 1 после нового курса 1; ошибка старого запроса после успешного retry; несовпадение schedule/status; сбой без первых данных. Человек повторяет критичный сценарий и случай отказа. После интеграции проверки выполняются на **объединённом состоянии**, поскольку отдельные успешные ветки не доказывают совместимость. Это действующее правило [AI workflow §4](ai_workflow.md), не новый gate.

### Учебная симуляция полного review / fix-up: счётчики дней

**SIMULATED — не выполненная разработка.** База и контракт взяты из среднего примера выше. Следующие diff/evidence и выводы — условные события упражнения, не реальные файлы, test output или утверждение о PASS. В настоящем шаге на каждом переходе прикладываются фактические материалы.

1. **Human intent:** «Нужно исправить счётчики: для моей группы они иногда завышены. API менять нельзя». Новый чат Qwen для этого шага.
2. **Qwen context → contract:** читает curated правила, доступный код фильтрации и требования счёта; замечает constraint «одна Lesson — одна единица, даже с несколькими группами». Согласованный контракт требует считать занятия выбранной группы/чётности, исключать чужую группу, показывать 0 и сохранять API/config. Для проверки нужны случаи из среднего примера; человек сверяет границы.
3. **Antigravity implementation → evidence:** в условном пакете есть base/HEAD/status, весь список файлов, diff используемого вычисления и тестов, вывод фактически выполненных проверок и UI-наблюдения. Общие изменения указаны «нет». Однако hunk показывает: после фильтра по группе и чётности вычисление складывает `lesson.groups.length`; тестовые входы содержат лишь одногрупповые занятия. Зелёный результат таких проверок не покрывал бы нужный negative case.
4. **Qwen review:** `FIX REQUIRED`. Severity: существенный дефект поведения. Evidence: операция суммирования в присланном hunk; одно подходящее занятие с `[G-A, G-B]` добавит 2 вместо 1 для G-A. Это контрпример по видимому коду, не заявление о самостоятельно воспроизведённом UI-сбое. В тестах нет требуемого multi-group acceptance. Стиль к дефекту не относится.
5. **Qwen targeted fix-up** передаётся исполнителю:

~~~text
Продолжи исходный контракт счётчиков из этого шага на текущем зафиксированном
base/HEAD + diff, не возвращай состояние к началу задачи. Objective прежний:
точное число занятий выбранной группы/чётности, без изменения API.
Дефект в присланном вычислении: lesson.groups.length считает группы,
а не записи Lesson; [G-A, G-B] даёт 2 вместо 1 для выбранной G-A.
Исправь только используемое вычисление в src/lib/client/day-lesson-counts.ts
и tests/client-day-counts.test.ts (в этой симуляции эти разрешённые файлы
уже созданы). Сохрани правильные фильтры, нулевой день и UI. Не меняй API,
schema, parser, dependencies, lockfile, config и не начинай redesign.
Одна подходящая multi-group Lesson должна давать 1; чужая группа — 0;
чётность и пустой день должны сохранить acceptance исходного контракта.
Повтори npm test -- tests/week-parity.test.ts tests/client-day-counts.test.ts,
npm run typecheck, npm run lint, npm run build и относящуюся проверку UI
через npm run dev. Верни обновлённый handoff по agent_task: точное состояние,
status/файлы/diff, фактический вывод, наблюдения, непроверенное и риски.
При необходимости расширить scope остановись и назови причину.
Не commit/push/merge/deploy в рамках этого задания.
~~~

6. **Antigravity updated evidence:** в условном повторном пакете виден подсчёт записей после прежних фильтров; добавлен контрпример с несколькими группами, есть реальные для этого условного запуска выводы всех запущенных проверок и наблюдения UI. Пакет фиксирует новое рабочее состояние, остальные изменения сохранены. Здесь эти выводы намеренно не выдумываются и не приводятся как настоящие логи.
7. **Qwen repeat review:** если обновлённый пакет действительно подтверждает все acceptance и не содержит существенных нарушений — `ACCEPTABLE`, с перечислением оставшихся границ/рисков. Если приложен только рассказ «исправил», результат будет `BLOCKED: MISSING EVIDENCE`, а не ACCEPTABLE.
8. **Human:** смотрит полный diff, объясняет файлы, повторяет критичный сценарий и проходит действующий Git gate. Решение о checkpoint/готовности PR, merge и release остаётся у уполномоченных людей; объединённое состояние проверяется после интеграции. Новый существенный шаг — новый чат с кратким итогом, fix-up этого шага уже завершён.

## 4. Несколько AI — по конкретной причине

| Действие | Кого подключить | Что считать полезным выходом |
|---|---|---|
| Неясно, где возникает сбой | Recon | Найденная цепочка и проверяемая гипотеза, без правок |
| Спор затрагивает общий контракт | Architect | Вариант, риск и probe для решения человеком |
| Контракт определён | Builder: основной Gemini в Antigravity | Узкое изменение и фактические проверки |
| Нужен поиск дефекта | Project Brain в исходном step-chat, независимый от Executor | Сверка evidence с контрактом, контрпример, verdict и targeted fix-up |
| Не хватает случаев приёмки | Test/eval | Входы, ожидаемые ответы и неизвестное; не меняет продуктовый код |
| Нужно проверить pitch | Judge simulation | Слабое утверждение и требуемое evidence, без выдуманных правил жюри |

Не просите три модели проголосовать, «всё ли правильно». Запущенный тест и воспроизведённый сбой сильнее их согласия. Reviewer получает требования, состояние и diff, а не просьбу подтвердить вывод Builder. Для обычного шага это возврат в исходный чат Project Brain; дополнительные роли подключаются только по конкретной необходимости. Люди принимают результат. Число одновременно работающих builders, worktrees, общие схемы и очередь интеграции регулируются в [AI workflow §3–4](ai_workflow.md); для одной небольшой задачи весь этот набор ролей не нужен.

## 5. Проверка готовности участника

Возьмите намерение своими словами и пройдите путь без подсказок автора документа. Готовность видна, если вы настроили Project с одним curated Source и четырьмя свободными местами, начали новый step-chat, дали намерение, получили самодостаточный контракт и diff в нужной ветке, вернули evidence в исходный чат, поняли recommendation и прошли targeted fix-up при дефекте. Человек должен объяснить scope, отличить выполненную проверку от обещанной, воспроизвести positive/negative case и понимать свои Git gates. Если застряли на контексте — вернитесь к [onboarding §3–4](ai_onboarding.md); на запуске или результате — к [execution guide](antigravity_gemini_workflow.md).

**RECOMMENDATION для будущих упражнений, не изменение curriculum.** По [team_rehearsal §8](team_rehearsal.md) повышать сложность по одной оси. После маленькой функции дать ограниченное изменение на стыке нескольких существующих компонентов с одним скрытым граничным случаем; затем отдельно интеграцию, отказ и передачу чужого кода. Так проверяются inspection, выбор контекста, разделение Recon/Build и verification, а не знание новой библиотеки.

Простая смена текста и изолированная функция с полностью выданным контекстом всё ещё решаются одним chat prompt; это не доказывает навык repository inspection. Даже сложный prompt можно скопировать. Поэтому смотреть нужно на найденные файлы, исходное состояние, объяснение одного ограничения и фактический контрпример. В drills B/C записывать уже принятые метрики через [drill_protocol](templates/drill_protocol.md), включая время до принятого результата и доработки; новый Drill G и обязательный турнир моделей не нужны.
