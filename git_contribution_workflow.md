# Fork → branch → clean diff → PR

**Срез: 8 сентября 2026. RECOMMENDATION.** Это командный runbook для учебных задач и будущих параллельных workstreams. Он не является правилом GigaHack.

Цель процесса проста: **каждый PR должен быть маленьким, актуальным, объяснимым и содержать только одну задачу**.

## 1. Термины

В этом документе:

- **upstream** — основной репозиторий команды;
- **origin** — личный fork участника;
- **main** — чистая копия актуального upstream `main`;
- **feature branch** — отдельная ветка ровно одной задачи.

Для учебного репозитория:

~~~text
upstream  https://github.com/barbalatv/utm-curs-i-orar-2027.git
origin    https://github.com/<your-login>/utm-curs-i-orar-2027.git
~~~

Проверка:

~~~bash
git remote -v
~~~

Если `upstream` ещё не добавлен:

~~~bash
git remote add upstream https://github.com/barbalatv/utm-curs-i-orar-2027.git
git fetch upstream
~~~

## 2. Перед каждым новым заданием

Новая задача начинается **не со старой feature-ветки**, а с обновления `main`.

~~~bash
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
~~~

Если `merge --ff-only` прошёл — локальный `main` не расходился с upstream.

Если команда отказалась выполнять fast-forward, **не делайте обычный merge автоматически**. Это означает, что в вашем `main` есть собственные commit или история разошлась.

### Если main случайно изменяли

Сначала убедитесь, что полезная работа сохранена в отдельной ветке.

~~~bash
git branch backup/main-before-sync
~~~

Если собственные commit в `main` не нужны и `main` должен быть точной копией upstream:

~~~bash
git fetch upstream
git reset --hard upstream/main
git push --force-with-lease origin main
~~~

`reset --hard` удаляет незакоммиченные изменения. Использовать его только после проверки `git status` и только для ветки, которую сознательно возвращаем к upstream.

## 3. Создание ветки задания

После sync:

~~~bash
git switch main
git switch -c task/<short-name>
~~~

Примеры:

~~~text
task/change-title
task/day-lesson-counts
task/failure-fallback
~~~

Не использовать для второго задания ветку первого. Не делать учебную задачу прямо в `main`.

Сразу после создания полезно проверить базу:

~~~bash
git log -1 --oneline
~~~

## 4. Во время работы

Перед изменениями прочитайте контракт задачи и определите ожидаемую область файлов.

Минимальная дисциплина:

- не менять соседние модули «заодно»;
- не обновлять зависимости без требования задачи;
- не коммитить `.env`, секреты, build output и generated-мусор;
- локальная ошибка запуска не даёт автоматического права менять общую конфигурацию;
- если AI предлагает изменить parser/domain/config для маленькой UI-задачи — остановиться и проверить причину;
- после заметного AI-изменения смотреть `git diff`, а не только браузер.

Полезные команды:

~~~bash
git status
git diff
git diff --stat
~~~

## 5. Перед commit

Сначала убедиться, что staged-набор содержит только задачу.

~~~bash
git status
git diff
git add <только нужные файлы>
git diff --cached
git status
~~~

Commit message должен описывать результат, а не факт работы.

Хорошо:

~~~text
feat: show lesson counts in day tabs
fix: preserve mobile day navigation
~~~

Плохо:

~~~text
Update
changes
fix
дзшка
~~~

Неформальные названия допустимы в личной песочнице, но общий contribution workflow должен тренировать handoff так же, как он будет выглядеть на хакатоне.

## 6. Перед PR: обязательный clean-diff check

Сначала получить свежий upstream:

~~~bash
git fetch upstream
~~~

Затем посмотреть **именно то, что увидит PR**:

~~~bash
git diff --stat upstream/main...HEAD
git diff upstream/main...HEAD
git log --oneline upstream/main..HEAD
~~~

Проверить три вопроса:

1. Есть ли в списке файл, который не нужен задаче?
2. Есть ли изменение из предыдущего задания?
3. Есть ли строка, которую я не могу объяснить?

Если хотя бы один ответ «да» — PR пока не открывается.

## 7. Upstream изменился, пока я работал

Если upstream ушёл вперёд, сначала оценить размер и риск своей ветки.

### Вариант A — короткая чистая ветка

Можно rebase:

~~~bash
git fetch upstream
git rebase upstream/main
~~~

После rebase снова выполнить тесты и clean-diff check.

Если ветка уже была опубликована в личный fork:

~~~bash
git push --force-with-lease
~~~

Использовать именно `--force-with-lease`, а не голый `--force`.

### Вариант B — ветка загрязнена или участник не уверен в истории

Для учебной задачи часто безопаснее **создать новую чистую ветку**:

~~~bash
git fetch upstream
git switch -c task/<name>-clean upstream/main
~~~

Если нужная работа уже оформлена отдельными правильными commit:

~~~bash
git cherry-pick <commit-sha>
~~~

Затем:

~~~bash
git diff --stat upstream/main...HEAD
git diff upstream/main...HEAD
~~~

Это отвечает на практический вопрос «зачем чистить старую ветку, если можно её удалить и скопировать main?» — **не обязательно чистить**. Если ветка не содержит ценного состояния, пересоздать её от свежего `main` обычно проще и надёжнее.

## 8. Когда ветку лучше выбросить

Пересоздавайте feature-ветку, если:

- она продолжает прошлое задание;
- она основана на сильно устаревшем main;
- в ней несколько несвязанных экспериментов;
- diff пытается отменить большое количество upstream-изменений;
- вы не можете объяснить историю commit;
- исправление Git занимает больше времени, чем перенос одного маленького нужного изменения.

Не сохраняйте ветку ради самой ветки. Сохраняйте **полезный diff**.

## 9. Push и PR

Первый push ветки:

~~~bash
git push -u origin task/<short-name>
~~~

PR открывается:

~~~text
base repository:  upstream repository
base branch:      main
head repository:  your fork
compare branch:   task/<short-name>
~~~

### Заголовок PR

Одно предложение о результате:

~~~text
feat: show current-week lesson counts on day buttons
~~~

### Минимальное тело PR

~~~markdown
## Что изменено
- ...

## Что проверено
- ...
- ...

## Evidence
- screenshot / test output / reproduction

## AI
- какой инструмент использовался;
- что после него было проверено или исправлено вручную.

## Ограничения
- ...
~~~

Для маленького учебного PR тело может быть короче, но три вещи обязательны: **что изменено · что проверено · чем это доказано**.

## 10. Review не означает merge

PR существует прежде всего как единица review и handoff. Для учебных заданий **не обязательно мержить каждый хороший PR в центральный `main`**.

Причины:

- разные участники могут решать одно и то же задание альтернативно;
- функция может быть полезна как упражнение, но не нужна продукту;
- merge учебного изменения создаёт новую базу и шум для остальных участников;
- последующий revert не возвращает историю к состоянию «ничего не происходило» и сам становится изменением main.

Поэтому maintainer отдельно принимает два решения:

1. **задача выполнена / PR принят как упражнение**;
2. **изменение действительно нужно продукту и должно быть merged**.

Не смешивать их.

## 11. Checklist автора перед запросом review

- [ ] Мой fork синхронизирован с upstream перед созданием ветки.
- [ ] Это отдельная ветка именно этого задания.
- [ ] `git diff upstream/main...HEAD` прочитан целиком.
- [ ] В diff нет предыдущего задания и случайных файлов.
- [ ] Я понимаю каждый изменённый файл.
- [ ] Положительный сценарий проверен.
- [ ] Проверен хотя бы один отрицательный/граничный сценарий.
- [ ] Responsive проверен, если затронут UI.
- [ ] Commit и PR названы по результату.
- [ ] PR содержит evidence.
- [ ] Я могу одним предложением объяснить, что делает изменение и зачем.

## 12. Checklist reviewer

Порядок review:

1. **Base:** ветка действительно основана на достаточно свежем upstream?
2. **Diff:** scope чистый?
3. **Behaviour:** контракт выполнен?
4. **Failure case:** что происходит на границе/ошибке?
5. **Regression:** соседнее поведение не откатилось?
6. **Ownership:** автор понимает diff?
7. **Merge decision:** это только хорошее упражнение или ещё и нужное изменение продукта?

Если base или diff явно плохие, нет смысла сначала обсуждать стиль кода. Попросите автора привести ветку к чистому состоянию и только потом продолжайте review.

## 13. На хакатоне

Модель fork не обязательна внутри одной команды — там удобнее отдельные worktree/ветки одного репозитория. Но правила переносятся напрямую:

- одна задача = одна зона изменений;
- base commit фиксируется в контракте AI-задачи;
- общий интерфейс не меняется молча;
- перед merge интегратор читает полный diff;
- незавершённая ветка не должна быть зависимостью зелёного main;
- маленький explainable diff ценнее большого «умного» diff;
- merge означает принятие ответственности, а не просто отсутствие конфликтов Git.
